Before publishing a page with structured data, compare the markup with what a visitor can actually read. The goal is an accurate description of the page, not the largest possible block of code or a promise about how search results will look.

## Compare each marked-up claim with the visible page

For each important property, ask: where can a visitor see this information? Check the business name, service, author, date, location, price, and any FAQ or review details you have included. If the information is not present, current, and relevant, remove it or update the page before publishing.

[Google's general guidance](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) says structured data should reflect visible content and accurately represent the page. That principle is a useful first review even when you're not targeting a specific rich result.

## Confirm the type fits the page

Ask what the page is mainly about and what the markup is meant to describe. A company page, service page, article, and video have different purposes. Choose the most specific type that genuinely fits, using Schema.org and the current Google feature documentation as references.

Don't add a type just because it appears in an example online. Examples may describe a different kind of page, a different feature, or older guidance.

## Check names, URLs, images, dates, and business details

Review the practical details that are easy to leave stale:

- Does the canonical page URL point to this page?
- Are the organization name and site URL correct?
- Are images relevant to the page and available to visitors?
- Do dates match the content and the displayed page?
- Are address, service area, hours, and contact details current?
- Do all referenced pages and profiles belong to the right organization?

If a redesign changed a URL or removed content, check for references that still point to the old version.

## Validate the markup without overreading the result

Use a relevant validator to catch syntax problems or missing fields. Read the result carefully: a test can report technical findings, but it cannot decide whether a business claim is true or whether the content is useful. A passing test also does not guarantee a rich result or a particular search display.

Keep a note of the page checked, tool used, findings, and any change made. If the tool flags a feature-specific requirement, verify that the feature applies to the page before changing the content or markup.

## Decide what needs fixing before launch

Fix incorrect visible facts first, then make the structured data consistent with those facts. Resolve broken URLs and unsupported content. Send unresolved implementation errors to the person who maintains the site with the page URL and exact diagnostic.

When the page and markup agree, publish through your normal review process and monitor Search Console if you use it. Monitoring can show whether Google has processed eligible structured data; it does not turn eligibility into a guaranteed display.
